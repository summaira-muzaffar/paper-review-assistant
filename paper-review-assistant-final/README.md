Paper Review Assistant
An LLM based tool that reviews academic papers automatically, paragraph by paragraph.
Upload a paper as a PDF and the tool extracts the full text, splits it into sections and paragraphs, and reviews every paragraph with a large language model. Each review comes back in a fixed structure: the issues found, each with a severity, an explanation, and a concrete suggested fix, plus the paragraph's strengths. The user can edit the review prompt for every single paragraph, so the review can be steered per paragraph, for example to check only statistics in one place and only clarity in another. All paragraph results are combined into one final report with an overall summary, which can be downloaded as a DOCX file.

Why this project exists
This project was built as an assessment task for Professor Tao Huanjie, School of Computer Science, Northwestern Polytechnical University, Xi'an, China. The task was to research and build an LLM based document and paper review auto generation tool: full text analysis of a paper, problem identification, and generation of revision suggestions, as a practical academic assistance tool.
The task has two hard requirements, and the design answers both directly:
The tool must have a software interface. It is a Streamlit web application with a custom theme, a settings sidebar, and a guided flow from upload to report.
The user must be able to set their own prompts for each paragraph. Every paragraph carries its own editable prompt, prefilled with a section aware default, stored under its own key so editing one paragraph never affects another, with a reset button per paragraph. This behaviour is covered by automated tests at the module level, in the interface, and at the model request level.
Features
PDF upload and text extraction with PyMuPDF, with clean handling of corrupt files and of PDFs with no extractable text
Rule based splitting into sections and paragraphs (known academic headings, numbered headings, capital headings), with long blocks from two column papers split into review sized chunks on sentence boundaries
One editable review prompt per paragraph, with a shared reviewer base prompt plus a focus line that adapts to the section type
Review through any OpenAI compatible API. The user enters their own API key, base URL, and model name in the sidebar, so DeepSeek works out of the box and no key is ever stored in the code or the repo
Structured results per paragraph: strengths, and issues with severity, explanation, and suggested fix
Review output in English or Chinese, and a bilingual interface (English main, Chinese toggle) for all labels
Final report view with totals, severity counts, strengths, and issues grouped by section
Overall summary generated by a second model pass over a compact digest of all findings
DOCX report export, verified by reading the exported file back in tests
Per paragraph failure isolation: one failed model call is recorded as an error for that paragraph and never discards the rest of the review
Settings validation and a Test API connection button: a key, base URL, and model from different providers are caught before any call, the provider is then checked with one small request, and every error is explained in plain language with the fix
Fast, calm free tier runs: paragraphs are reviewed in small batches (up to 5 paragraphs, up to 8,000 characters per call), so a 38 paragraph paper needs about 10 calls instead of 38, and batches run in parallel waves of 3 with call starts spaced 2 seconds apart. Every paragraph missing from a batch answer is reviewed again on its own, so batching can never drop one. A batch that hits the provider limit gets one short pause and one retry, then it is split into smaller batches, down to single paragraphs, because per minute token rations refuse large requests that smaller ones fit under; if several batches in a row still end limited, the run stops calling the provider and saves the rest for later at once. Before a run even starts, the connection check proves a real review call works, so a spent quota fails once with a clear explanation instead of failing on every paragraph
Live progress display: while a run works, the progress bar shows the paragraph count and percentage, a status line reports the running tally of reviewed paragraphs and any saved for later, and the run ends with an exact reviewed count and clear next step instead of a bare done message
Resumable runs: pressing Run review again keeps every paragraph that already succeeded and reviews only the missing and failed ones, so a rate limited free tier run is finished by waiting and rerunning, never by starting over
Progress saved automatically: results are written to disk after every paragraph (never the API key), so a closed tab, a sleeping laptop, or a restarted app cannot wipe a half done run. Uploading the same paper again restores its finished paragraphs, and a Start fresh button clears one paper's saved progress

How it works
PDF upload
  -> text extraction, page by page (src/pdf_extract.py)
  -> section and paragraph splitting (src/segmentation.py)
  -> one prompt per paragraph, defaults plus user edits (src/prompts.py)
  -> batched model calls, each paragraph under its own id with its own prompt, structured JSON answer (src/llm_client.py)
  -> aggregation, overall summary, DOCX report (src/report.py)
Interface: app.py (Streamlit). All interface labels in English and
Chinese live in src/i18n.py.
Each stage is a small module with one job, and each was built and tested in its own step. BUILD_LOG.md records every step: what was done, how, the decisions and why, and the exact test results.
How to run
pip install -r requirements.txt
streamlit run app.py
Then, in the page that opens:
Enter your API key, base URL, and model name in the sidebar (the defaults are DeepSeek's address and deepseek-chat). The three values must come from the same provider.
Press Test API connection. It confirms the key is accepted and the model exists before you spend a full run.
Choose the review language, English or Chinese.
Upload a paper as a PDF. The extracted text and the paper structure appear.
Edit any paragraph's prompt if you want a different focus for that paragraph.
Press Run review and watch the progress bar. Results appear per paragraph.
Generate the overall summary, and download the report as DOCX.

Testing
45 automated tests across 6 test files cover extraction, splitting, per paragraph prompt isolation (including proof that a custom prompt reaches the model for its own paragraph only), structured answer parsing, batched reviewing (one call carrying several paragraphs, each with its own prompt, with fallback for any paragraph a batch answer misses), failure isolation, settings validation and the preflight connection check, the batch rate limit policy (one short pause and retry, adaptive splitting of refused batches down to single paragraphs, saved for later marking, and the circuit breaker that stops calling a spent provider), plus a connection check that ends with a real test generation call so a spent quota fails before a run starts, resumable runs that keep earlier successes, progress saving and restoring from disk, plain language error translation, aggregation, summary generation (including a size bounded summary digest for very large reports), and DOCX read back:

Known limitations
Scanned, image only PDFs contain no extractable text. The tool reports this clearly instead of inventing a review. OCR is out of scope.
The review is based on the extracted text. Figures and graphs themselves are not analysed, so the tool cannot judge whether a chart supports the claim made about it; figure captions and table text that live in the text layer are reviewed as ordinary text. Analysing figure images with a vision language model is future work.
Section detection is rule based and tuned for research papers. Figure and table labels can occasionally be mistaken for a heading, and documents that are not papers (CVs, transcripts) split less precisely, though they still complete the pipeline.
Review quality depends on the model and the prompts chosen. The tool structures and presents model feedback; it does not guarantee the feedback is correct, and a human should read the report before acting on it.
